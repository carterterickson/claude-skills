# Execution adapters and current boundaries

> **Implementation status (runtime 0.1.0, 2026-09-23, macOS).** The common interface is implemented by `scripts/xao.mjs`:
> inspect = `inspect [--probe-app-server]`; prepare = `assign`; start/events/respond/cancel/collect = `run-codex` / `run-bridge`;
> native routes = `dispatch-native` + `record-native`. Route D is `scripts/adapters/codex-app-server.mjs`, mapped from the schema
> generated by codex-cli 0.155.0-alpha.16.3. On this Mac it is **static-ready**: handshake, model/list and config/read confirmation
> of the leaf controls passed with no prompt, but it is not runtime-verified until a live run records evidence. Follow-up is
> implemented at the protocol level (same thread) but not exposed as a CLI command yet. Descendant cleanup is verified by
> process-group checks on macOS. Windows cleanup is unverified.

The shared coordinator owns dispatch. Native host tools stay native; external processes run only through reviewed adapters within effective host permissions. A leaf planner may propose worker assignments but cannot dispatch them itself. No attempt to bypass managed tool restrictions using another CLI is allowed.

All initial adapters execute on the current host device. A remote desktop connection does not move process execution to the viewing machine. Route discovery must record reachability and access to the actual source, not just a model's existence somewhere. Cross-device work uses the explicit quiescent transfer in continuity.md; remote dispatch or a distributed ownership service is outside this initial build.

## Common adapter interface to implement

These are **proposed internal operations**, not existing terminal commands or tool names:

| Operation | Contract |
| --- | --- |
| inspect | Sanitized executable/version, auth class, model discovery, tools, policy and capability status; no inference |
| prepare | Resolve exact baseline/workspace and assignment; validate ownership and permission envelope |
| start | Start one bounded role assignment with a stable idempotency key; return actual session/process identifiers |
| events | Progress and individually identified approval requests; stdout protocol separate from diagnostics |
| respond | Decide only the matching pending invocation and complete input; reject stale/duplicate/mismatched responses |
| follow-up | Available only if explicitly supported and linked to the same real session |
| cancel | Stop owned work, report terminal state and cleanup evidence; never infer completion from silence |
| collect | Actual changed/untracked inventory, verification, observed route and usage provenance |

Capability fields distinguish `supported`, `unsupported` and `unknown` for follow-up, approvals, read-only isolation, cancellation, descendant cleanup, tools and metering. Preserve user input requests, errors and partial results. One terminal event per run; a lost connection is not success. If start acknowledgement is lost, inspect the known run before retrying the same key; never launch a speculative duplicate writer.

This host and adapter may auto-allow some in-scope actions under standing permissions. The requirement is to preserve the effective host/project policy, not to invent a prompt for every read or ordinary edit. Reject any adapter that would broaden the policy or cannot expose an action needing approval.

## A. Codex host → native workers

Use actual native delegation tools and roles discovered in the current session. The existing `astra_flash_builder` role pins `deepseek/deepseek-v4.1-flash`; it is a Codex role, not a Claude model alias. Inspect root/profile/project overrides. Confirm observed child/provider routing from correlated host/Router records after authorized use. Keep the current root unchanged.

Use the host's real lifecycle/wait tools and mark completed children done. A role name does not imply an isolated worktree. An inherited Flash route may also affect default reviewer roles; choose reviewers explicitly through supported routes rather than assuming a generic child is a frontier reviewer.

## B. Codex host → Claude via the existing bridge

Reuse the installed `model-council/scripts/claude_bridge.mjs` with its supported device-local source and official SDK/CLI. Read the installed bridge reference before dispatch. The package includes a reference snapshot of that contract for the implementer; it is not authority to downgrade the live bridge.

Preserve subscription auth, the no-API-fallback rule, hook handshake, exact model/credential/tool checks, per-invocation controller approval, protected state and owned-process cleanup. Current legacy behavior: committed Git base, separate retained worktree, no dirty-work copying, no resume, no automatic integration, no SDK token counters. Windows descendant cleanup has a known evidence gap. Do not claim those features were added by this specification.

For a dirty candidate, supply a reviewed exact snapshot or bounded diff and state what the model can actually inspect. If the lead needs files/tools that the bridge cannot expose, use another eligible route or keep that role in the host. Never accept review of old HEAD as review of the current candidate.

## C. Claude host → native Claude workers

Use native subagents when the installed Claude Code supports the requested model, tools, isolation and continuation. Record the resolved model, not just the alias. Respect project and managed restrictions. Use read-only tool lists for reviewers and disable recursive delegation for every leaf role. The shared coordinator remains in the foreground.

Claude's official [subagent documentation](https://code.claude.com/docs/en/sub-agents) describes per-agent models and tools; availability and any substitution must be verified on the installed version. Native subagent definitions alone do not establish that DeepSeek or Codex models work in a subscription-backed Claude session.

## D. Claude host → Codex planner or Flash worker: new adapter

Preferred initial integration: a narrow client of the installed **Codex App Server**, launched as an owned local process over stdio. This is a design choice to implement and validate, not a route already demonstrated here. Use the actual normal-user executable/profile; desktop, PATH and remote execution contexts may differ.

Official docs describe schema generation, model discovery, thread/turn lifecycle and approval events. Generate or inspect schemas for the exact binary and verify all message fields. Use discovered models and efforts. Keep existing ChatGPT login with the official client; no token copying or subscription proxy. [App Server](https://learn.chatgpt.com/docs/app-server), [authentication](https://learn.chatgpt.com/docs/auth).

Proposed sequence: initialize → inspect account/model metadata without exposing identity/secrets → select a permitted route → establish thread with explicit workspace and effective permission envelope → submit bounded role task → service events/approvals → collect terminal evidence → close owned session/process. Map actual protocol shapes in implementation rather than guessing JSON fields from this document. Do not attach to or take control of unrelated desktop tasks. An external Codex session may lack desktop-only tools/plugins and is not necessarily visible as the same app task.

For Flash, use the configured Router-backed model only if this adapter context actually supports it. This creates a bounded external Codex **worker session**, not a native Claude subagent or necessarily an `astra_flash_builder` child. Disable orchestration/delegation for that worker using supported controls and a scoped brief. Verify provider/model correlation, real tools and same-session continuation separately. If no exposed control can enforce required no-delegation/tool restrictions, mark the capability unsupported and do not run that assignment.

For a Codex planning lead, enforce read-only access to the exact snapshot or supply bounded material for analysis. Planning outputs contain contracts, not executable commands to run blindly. A provider/model mismatch fails the assignment or triggers an explicitly disclosed eligible substitution before continuing.

Do not weaken Windows sandbox/approval rules to launch this adapter. A normal-user Claude process may have different host permissions from a Codex sandbox; record and honor the initiating host's effective limits. Explicitly compare sandbox, filesystem, network and approval scope before starting the subprocess. A local process boundary is not itself a sandbox.

## E. Optional existing routed Claude launcher

The inspected Router source also has `claude-router`, a separate launcher using the Router's Anthropic Messages compatibility surface. It changes process-local provider/model settings, including agent defaults, and its docs explicitly say non-Claude routed models are not an Anthropic-supported Claude Code configuration. It does not provide cross-app task continuity or mix normal Claude subscription calls into the same Router catalog by itself.

Do not make it the default for this workflow. It may be evaluated later as a **separate bounded Flash process** if already authorized and if it passes equivalent permission, model, tool, metering and cleanup requirements. Never set global Claude model aliases or provider environment variables to Flash merely to make workers cheaper. Do not enable `anthropic-api` to turn subscription access into an API route. Preserve normal Claude login.

## Device and recovery rules

Inspect the actual process identity on each device. `USERPROFILE` is not identity. Respect no-discovery policy, fail invalid explicit source/binary overrides, keep credentials local and use hidden supported prompts for required provider setup. No automatic paid probe or retry; a detached probe may continue after its wrapper exits. Record exact revisions and protected backups before install. Do not mutate active catalogs, global model defaults or unrelated projects for route discovery.

On timeout/EOF/error, cancel and verify owned process cleanup before replacement or handoff. Leave unresolved state blocked if a writer may remain active. Preserve worktrees and partial outputs for review. Never kill every process named Node, Claude or Codex, and never blindly restore stale config over intervening changes.
